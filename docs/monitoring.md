# Мониторинг и наблюдаемость

## Технические метрики

- **Latency**: p50/p99 быстрого пути (цель p99 ≤ 500 мс), отдельно p99 классификатора; latency async-генерации end-to-end.
- **Throughput и очереди**: тикетов/мин по каналам; глубина и возраст сообщений в `generate-reply` и `operator-inbox`.
- **Ошибки**: error rate по компонентам; таймауты/5xx LLM API; состояние circuit breaker (open/closed).
- **Насыщение**: CPU/память воркеров, лаг консьюмеров.

## ML-метрики (онлайн)

- **Распределение confidence** классификатора и **доля low-confidence** (sudden shift = сигнал проблемы).
- **Распределение по категориям** входящего потока (для отделения дрейфа данных от деградации модели).
- **Accept rate черновиков** оператором (главный онлайн-прокси качества генерации).
- **Доля эскалаций** по причинам (risky_topic / low_confidence / no_grounding / pii).
- **Retrieval score**: средний и доля запросов ниже порога grounding.
- **Дедупликация при инцидентах** (см. [architecture.md](architecture.md)): dedup ratio (тикетов на кластер), false-merge rate по выборочному аудиту (главный guardrail качества), time-to-first-status во время инцидента, cluster purity.
- Регулярный офлайн-прогон на замороженном golden set (регрессия качества при обновлениях модели/промпта).

## Продуктовые / бизнес-метрики

Полный список с порогами — в [product.md](product.md). Отслеживаем в дашборде: North Star — доля тикетов, закрытых без оператора при неухудшении CSAT; guardrails — reopen rate, CSAT, SLA breach rate; плюс стоимость обработки тикета (₽) и экономия часов операторов.

## Стартовые алерты

| Алерт | Порог (старт) | Действие |
|---|---|---|
| p99 быстрого пути | > 500 мс, 5 мин | on-call: проверить классификатор/БД |
| Глубина operator-inbox | > 2× дневной нормы | включить инцидентный режим (дедупликация) |
| LLM error rate | > 10%, 5 мин | circuit breaker должен открыться; проверить |
| Доля low-confidence | > 2× бейзлайна за час | возможен дрейф потока или деградация |
| Reopen rate авто/suggest-ответов | > 11% (бейзлайн 9% + 2 п.п.) | остановить автозакрытие (kill switch) |
| Расход LLM-бюджета | > 80% дневного лимита | деградация до шаблонов + уведомление |
| PII-детект в исходящем ответе | > 0 | немедленно: блокировка автоответов |

## Деградация модели vs изменение входящего потока

Ключ — смотреть на **вход** и **выход** раздельно:

1. **Изменился вход** (дрейф потока): сместилось распределение категорий/каналов/длины текста, embedding-дрейф входящих тикетов (population stability index по кластерам). Confidence падает *вместе* со сдвигом входного распределения → это инцидент или новая тема, а не поломка модели. Реакция: инцидентный режим, доразметка новой темы.
2. **Деградировала модель**: входное распределение стабильно, но упали accept rate черновиков / выросли reopen / упало качество на еженедельном прогоне golden set → проблема в модели/промпте/KB. Реакция: откат версии модели или промпта (версии фиксируются в audit log).

## Мониторинг стоимости LLM

- Счётчики токенов (prompt/completion) на каждый вызов → ₽/тикет, ₽/день, разбивка по категориям.
- Жёсткий дневной бюджет с автоматической деградацией до шаблонов при исчерпании.
- Алерт на аномальный рост ₽/тикет (напр., раздувание промпта после изменения retrieval).

## Решается ли исходная задача

Еженедельный отчёт по цепочке: доля потока, обработанного без оператора → сэкономленные часы операторов → SLA первого ответа → CSAT и reopen на автоматизированных категориях vs ручных. Если автоматизация растёт, а CSAT/reopen ухудшаются — система «оптимизирует не то», разбор обязателен. Дополнительно: выборочный ручной аудит N=50 автоответов в неделю по чек-листу качества.
