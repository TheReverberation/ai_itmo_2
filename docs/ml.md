# ML/LLM-дизайн

Принцип: **самый дешёвый инструмент, решающий задачу с нужным качеством**. LLM — только там, где без генерации не обойтись, и никогда на горячем пути: на 200k тикетов/день каждый лишний вызов LLM — это прямые расходы и потеря производительности.

## Карта задач и подходов

| Задача | Подход | Почему |
|---|---|---|
| Нормализация каналов | правила | Детерминированно, дёшево |
| PII-детекция и маскирование | Presidio: распознавание паттернов (email/телефон/карта) + NER (открытая модель, напр. Natasha / DeepPavlov) | Паттерны ловят контакты и карты; NER — имена и адреса. |
| Классификация темы | классический ML: TF-IDF + логрег (baseline) → лёгкий трансформер | Укладывается в ≤200 мс на CPU, дёшево на 200k/день, качество измеримо |
| Классификация риска | правила (стоп-категории) + небольшая LLM | Риск-список должен быть определен перед моделью: статичное правило перебивает любую уверенность модели |
| Поиск похожих тикетов / статей KB | embeddings + retrieval | Retrieval даёт grounding для генерации и похожие решённые тикеты |
| Дедупликация при инцидентах | clustering по embeddings (cosine + порог + окно времени); в PoC — Jaccard по токенам + blocking по теме | Дёшево, работает на пиках: 10–20k похожих тикетов схлопываются до генерации |
| Генерация черновика ответа | LLM API (managed) c контекстом из retrieval | Единственное место, где нужна генерация |
| Суммаризация тикета для оператора | LLM, та же инфраструктура | Тот же async-путь |
| Решение «закрывать ли автоматически» | **не LLM**: правила + confidence + gate | Решение о действии должно быть объяснимым и аудируемым |

## Где LLM использовать НЕ стоит

- **Классификация/маршрутизация** — дорого (200k вызовов/день), медленно (>500 мс), нестабильно; классический ML лучше по всем осям.
- **PII-детекция** — нельзя отправлять сырой текст во внешний API.
- **Финальное решение об автозакрытии** — нужен детерминированный, объяснимый gate.
- **Инцидентные пики** — 10–20k генераций за 10 минут бессмысленны и дороги: нужна дедупликация и один статус-ответ.

## Baselines: что запускаем первым

1. **Правила по ключевым словам** для темы и риска (в PoC именно это) — точка отсчёта и вечный fallback.
2. **TF-IDF + логистическая регрессия** на исторических тикетах — первый обучаемый baseline; ожидаемо покрывает большинство типовых категорий.
3. **TF-IDF/BM25 retrieval** по KB — baseline поиска до внедрения embeddings.
4. Только после измерения baseline — трансформеры, если прирост оправдывает стоимость.

Такой порядок даёт работающую систему и честную точку сравнения для каждого усложнения.

## Откуда берутся модели и какие данные нужны

- **Открытые предобученные**: `rubert-tiny2` (классификация, дообучение), `e5`/`sbert` (embeddings, без дообучения на старте), NER из Natasha/DeepPavlov. Внешний LLM — managed API (или внутренний хостинг open-weights, если требования privacy запретят внешний API — решение фиксируется на этапе security review); выбор провайдера — по бенчмарку на своих тикетах, а не по общим лидербордам.
- **Данные для обучения классификатора**: исторические тикеты с итоговой категорией из helpdesk (слаборазмеченные «бесплатно» — категория, проставленная оператором при закрытии). Нужно ~5–20k размеченных примеров на запуск.
- **Данные для retrieval**: статьи KB + пары «тикет → ответ оператора» с высоким CSAT.
- **Постоянный источник свежей разметки**: decision log + правки операторов в suggest-режиме — доля черновиков «принят без правок / с мелкими правками / переписан» является метрикой качества генерации, **не требующей отдельной разметки**.

## Разметка исторических данных

1. Выгрузка закрытых тикетов за 6–12 месяцев; категории операторов — как noisy labels.
2. Чистка: стратифицированная выборка ~2–3k тикетов, ручная перепроверка разметчиками (2 разметчика + арбитраж, меряем inter-annotator agreement, Cohen's kappa ≥ 0.7).
3. Отдельная разметка **риск-флага** (можно/нельзя автоматизировать) — только силами senior-агентов поддержки, т.к. цена ошибки высокая и асимметричная.
4. Golden set ~500 тикетов — замораживается для регрессионного тестирования моделей и промптов.
5. Пары «тикет → правильная статья KB» для оценки retrieval (recall@5): берутся из ответов операторов, где есть ссылка на статью KB, + ручная проверка выборки этих пар.

## Валидация качества

- **Офлайн**: golden set, стратифицированный по категориям, + **holdout по времени**. Отдельный тест-сет по риск-категориям, намеренно пересемплированный по риск-позитивам. Регрессионный прогон при каждом изменении модели/промпта.
- **Shadow mode**: система работает на живом потоке, решения записываются, но не применяются; сравнение с действиями операторов.
- **Suggest mode**: доля принятых оператором черновиков (accept rate) — главный онлайн-сигнал качества генерации.
- **A/B на автозакрытии**: только для безопасных категорий; guardrails — reopen rate и CSAT (см. [product.md](product.md) / [monitoring.md](monitoring.md)).

## Обработка низкой уверенности

Единая политика на всех уровнях: **сомневаешься — отдай человеку.**

- Классификатор отдаёт calibrated confidence. Порог эскалации выбирается на валидации как компромисс «доля автоматизации vs ошибка» — это **продуктовое решение**, а не только техническое. После каждого переобучения калибровка перепроверяется и порог перевыбирается на валидации (порог — конфигурация, деплой не нужен).
- Рискованная категория → эскалация независимо от confidence.
- Gate после генерации: нет PII в ответе + groundedness-проверка; не прошёл → черновик оператору, а не пользователю.
- Все пороги — конфигурация, не код; меняются без деплоя и логируются в audit. В suggest-режиме confidence показывается оператору вместе с черновиком, чтобы калибровать доверие.
