# ML/LLM-задачи системы

Принцип: **самый дешёвый инструмент, который решает задачу**. LLM — последний уровень каскада, а не решение по умолчанию: на 200k тикетов/день каждый лишний вызов LLM — это прямые деньги и латентность.

## Каскад «правила → классическая ML → embeddings → LLM»

| Задача | Инструмент | Почему не проще / не сложнее |
|---|---|---|
| Детект PII (email, телефон, карта) | Presidio (pattern-рекогнайзеры) + лёгкий локальный NER | детерминированность и recall важнее гибкости; LLM для PII — это отправить PII наружу, чтобы узнать, что это PII |
| Рискованные категории (оплата-споры, ПДн, безопасность, юр.) | правила поверх классификатора | политика должна быть объяснимой и переопределять любую модель; false negative здесь дороже всего |
| Классификация темы (hot path, ≤500 мс) | классическая модель: TF-IDF/fastText + логрег или лёгкий градиентный бустинг; следующий шаг — эмбеддинги + логрег | укладывается в миллисекунды на CPU, дёшево на 200k/день; LLM на hot path не проходит ни по латентности, ни по стоимости |
| Приоритизация / SLA-маршрутизация | правила по метаданным (канал, тариф, возраст тикета) | ML не даёт преимущества над явной бизнес-политикой |
| Поиск похожих тикетов и статей KB | открытая embedding-модель (напр. multilingual-e5 / sbert-ru) + vector store | ключевая задача семантическая, правилами не решается; в PoC заменена TF-IDF |
| Дедупликация при инцидентных всплесках | кластеризация по эмбеддингам (близость + окно времени) | 10–20k похожих тикетов должны схлопнуться в один инцидент до генерации |
| Черновик ответа, суммаризация треда для оператора | LLM (внешний API, вход только маскированный) | единственная задача, где нужна генерация; асинхронно, вне SLA hot path |

**Где LLM использовать не стоит:** hot-path классификация и маршрутизация, PII-детект, приоритизация, любые решения, требующие детерминированной политики (что можно автозакрывать). Там LLM дороже, медленнее и хуже аудируется.

## Baselines — что запускаем первым

1. **Правила по ключевым словам** (как в PoC) — базовая линия и вечный fallback.
2. **TF-IDF + логистическая регрессия** на исторических тикетах — обычно закрывает большую часть качества классификации тем.
3. **Открытые эмбеддинги + логрег / kNN** — если (2) не дотягивает по редким классам.
4. Fine-tuning или LLM-классификация — только если (2)–(3) доказуемо недостаточны на holdout.

Такой порядок даёт работающую систему до появления «настоящего ML» и честную точку сравнения для каждого усложнения.

## Откуда модели и данные

- **Модели:** открытые (эмбеддинги — multilingual-e5/sbert; NER — Natasha/DeepPavlov; классификатор обучается внутри на своих данных). Внешний LLM — управляемый API; выбор конкретного провайдера — по бенчмарку на своих тикетах, а не по общим лидербордам.
- **Данные для обучения классификатора:** исторические тикеты с действиями операторов. Категория, в которую оператор в итоге отнёс/чем закрыл тикет — это **слабая разметка**, покрывающая весь исторический объём бесплатно.
- **Разметка:** стратифицированная выборка 3–5k тикетов на ручную проверку слабой разметки (двойная разметка ~10% для оценки согласованности, спорные случаи — тимлиду поддержки). Отдельно размечается `risk` — там нужен полный ручной контроль, потому что цена ошибки асимметрична.
- Далее decision log + правки операторов в suggest-режиме становятся постоянным источником свежей разметки (см. [monitoring.md](monitoring.md)).

## Валидация качества

- **Классификатор:** holdout по времени (train — прошлое, test — последние недели, чтобы честно ловить дрейф), метрики per-class precision/recall/F1. Для `risk` — целевой **recall ≥ 0.95** (пропустить рискованный тикет хуже, чем лишний раз эскалировать); допустимый precision подбирается по нагрузке на операторов.
- **Калибровка confidence:** reliability-диаграмма / Brier score; порог эскалации (в PoC — 0.55) выбирается на валидации как компромисс «доля автоматизации vs ошибка», и это продуктовое решение, а не только техническое.
- **Retrieval:** recall@k на парах «тикет → статья, которой оператор реально ответил».
- **Черновики LLM:** в shadow/suggest-режиме — доля черновиков, отправленных оператором без правок / с мелкими правками / переписанных; это метрика качества генерации, не требующая отдельной разметки.

## Обработка низкой уверенности

Единая политика на всех уровнях: **сомневаешься — отдай человеку.**
- `confidence < порога` у классификатора → эскалация оператору без генерации;
- retrieval score ниже порога → черновик не генерируется (нельзя давать LLM отвечать «из головы» без опоры на KB);
- рискованная категория → эскалация независимо от confidence;
- в suggest-режиме confidence показывается оператору вместе с черновиком, чтобы калибровать доверие.
