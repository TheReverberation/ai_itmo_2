# SELF_REVIEW

## Самая слабая часть решения

Классификатор PoC: правила по ключевым словам с эвристическим confidence. Confidence теперь учитывает объём сигнала и отрыв лидера от конкурентов (единичное слабое совпадение честно уходит в low-confidence → оператор), но это всё равно эвристика, а не калиброванная вероятность модели — заглушка контракта `(topic, confidence, risky)`, а не прототип. Вторая слабость — расчёт эффекта опирается на допущение «автоматизируем половину типовых», которое до shadow mode ничем не подтверждено.

## Сделанные предположения

- 40% типовых тикетов действительно автоматизируемы хотя бы наполовину (проверяется в shadow mode).
- Историческая разметка категорий операторами достаточно чиста для baseline после ручной чистки 2–3k примеров.
- Внешний LLM API допустим при условии маскирования PII (если security review запретит — нужен внутренний хостинг open-weights, экономика ухудшится).
- Ставка LLM ≈ 3 ₽/тикет — грубая оценка, чувствительна к длине контекста retrieval.

## Нерешённые риски

- Prompt injection закрыт промпт-изоляцией и выходным gate (в PoC — символически: PII-плейсхолдеры + groundedness), но нет системной защиты (adversarial-тесты, red teaming, LLM-judge).
- Мультиязычность и вложения (скриншоты) не рассматривались.
- Деградация KB (устаревшие статьи) → уверенные, но неверные черновики; нужен процесс актуализации KB, он не спроектирован.
- Поведение операторов: риск «автопринятия» черновиков без чтения (automation bias) — нужен контроль качества принятых ответов.

## Что можно улучшить за 2 дополнительных дня

1. Заменить правила на TF-IDF+логрег, обученный на синтетическом/открытом датасете, с настоящим calibrated confidence.
2. Embeddings-retrieval (sentence-transformers) вместо TF-IDF + оценка recall@5 на мини-golden-set.
3. Подключить реальный LLM API за circuit breaker с подсчётом токенов и бюджетом.
4. FastAPI-обёртка + docker-compose с очередью, чтобы показать sync/async разделение делом.

## Что доработать перед production

Очереди и ретраи, идемпотентность обработки, версионирование моделей и промптов, PII-NER, интеграция с helpdesk, нагрузочное тестирование пикового сценария (20k/10 мин), процесс разметки и переобучения, kill switch и runbook для on-call.

## Что не стоит автоматизировать полностью

Платежи и возвраты, безопасность аккаунтов, юридические претензии и жалобы, любые обращения с признаками угрозы жизни/здоровью, а также решение о **расширении** списка автозакрываемых категорий — это всегда решение человека на основе данных пилота, а не системы.

## Какие данные пилота убедили бы остановить проект

Если в shadow mode на реальном потоке: (а) macro-F1 классификатора < 0.7 после доразметки — поток слишком неоднороден для дешёвой классификации; (б) accept rate черновиков < 20–25% — генерация не помогает операторам, а мешает; (в) реальная доля «автоматизируемых» тикетов < 10% потока — экономика не сходится даже при идеальном качестве; (г) reopen rate на пилотном автозакрытии стабильно > 12–13% при неоднократных итерациях качества — система вредит пользовательскому опыту быстрее, чем экономит деньги. Любой из пунктов (а)–(г), не исправленный за 2–3 итерации, — основание остановить проект и оставить только маршрутизацию.
