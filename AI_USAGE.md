# AI_USAGE

Работа велась с AI-ассистентом (агентный режим в VS Code). Ниже — честное описание роли AI по этапам.

## Как AI использовался по этапам

- **Понимание задачи и декомпозиция**: AI извлёк текст задания из PDF и составил план выполнения с таймлайном (`ai_plant_for_me.md`). Решение о порядке работ (архитектура до PoC) принял я — план AI изначально предлагал стандартную последовательность.
- **Проектирование архитектуры**: AI сгенерировал первый вариант architecture.md с Mermaid-диаграммами. Ключевые решения зафиксированы мной как требования до генерации: LLM не на горячем пути, правила риска детерминированно сильнее модели, деградация ступенями (LLM → retrieval-only → шаблон → оператор).
- **Выбор ML/LLM-подходов**: AI предложил карту «задача → инструмент». Я подтвердил принцип «самый дешёвый инструмент, решающий задачу» и настоял, чтобы решение об автозакрытии не принимал LLM — только детерминированный gate.
- **Разработка PoC**: код PoC написан AI по согласованной структуре. Моё ограничение: только stdlib, без зависимостей — чтобы PoC гарантированно запускался у проверяющего одной командой.
- **Тесты и документация**: smoke-тесты и docs сгенерированы AI, прогнаны реально (7/7 ok), выводы demo проверены глазами на осмысленность.
- **Поиск рисков и edge cases**: списки рисков — совместно; тикеты t-006 (юридическая угроза) и t-007 (неклассифицируемый мусор) добавлены специально для проверки, что «непонятное» не автозакрывается.

## Где предложения AI были отклонены / скорректированы

- Первый вариант классификатора использовал `max(scores, key=scores.get)` — статический анализатор дал ошибку типов; заменено на явную лямбду. Обнаружено немедленно по диагностике Pylance.
- Черновой план предполагал FastAPI-сервис для PoC; отклонено мной как лишний скоуп — CLI-скрипт демонстрирует те же контрактные точки без зависимостей и настройки окружения.
- Первая версия смоук-теста содержала бессмысленный assert (`assertIn(x, (True, False))` — тавтология, всегда истинна). Найдено при ревью кода теста, заменено на осмысленную проверку маскирования карты.

## Примеры ошибок AI и как они были пойманы

1. **Хрупкий/тавтологичный тест** (выше): тест, который не может упасть, хуже отсутствия теста — создаёт ложную уверенность. Пойман ручным ревью diff'а, исправлен.
2. **Обрыв генерации длинных файлов**: architecture.md и product.md при первой записи обрезались на середине предложения. Обнаружено сверкой записанного содержимого с планом раздела; файлы дописаны/перезаписаны. Вывод: генерацию больших документов нужно проверять на целостность, а не доверять «успеху» записи.
3. **Слишком общие формулировки**: первые версии value proposition для оператора/пользователя/бизнеса отличались словами, но не сутью (все сводились к «быстрее и дешевле»). Переписаны так, чтобы у каждой роли была своя механика ценности (оператор — смена характера работы, пользователь — время и точность маршрута, бизнес — масштабирование без роста ФОТ).

## Ключевые решения, принятые мной

Разделение sync/async с бюджетом 500 мс; risk-список как правило поверх модели без исключений; PoC без автоотправки пользователю (всё через оператора — соответствует suggest-этапу); stdlib-only; обязательный тест fallback-а LLM; консервативные цифры в расчёте эффекта (смешанные 75 ₽/тикет вместо оптимистичных 150 ₽).
