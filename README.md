# Автоматизация обработки тикетов поддержки — System Design + PoC

Отборочное задание (Задание 2, System Design), программа «Искусственный интеллект».

## Что делает решение

Спроектирована AI/ML-система обработки тикетов поддержки (200k/день, пики 10–20k за 10 минут) с разделением на **горячий синхронный путь** (PII-маскирование → классификация темы/риска → маршрутизация, ≤500 мс, без LLM) и **холодный асинхронный путь** (очередь → retrieval по базе знаний → черновик ответа LLM → human-in-the-loop). Рискованные и low-confidence тикеты никогда не закрываются автоматически; при недоступности LLM система деградирует до маршрутизации без черновиков; все решения пишутся в аудируемый decision log.

## Зачем это бизнесу

Поддержка тратит ~8 минут оператора (150 ₽) на каждый из 200k тикетов в день, при этом ~40% потока — типовые повторяющиеся вопросы. Система снимает с операторов черновую работу по типовому потоку: даже консервативная автоматизация 20% тикетов — это порядка 40k тикетов/день и **~2 млрд ₽ в год** валовой экономии операторского времени (до вычета стоимости LLM и эксплуатации — на этом объёме это единицы процентов от экономии). Не менее важно: типовые обращения получают ответ за минуты вместо ожидания в общей очереди, а операторы концентрируются на сложных случаях. Guardrails (reopen rate, CSAT, SLA) гарантируют, что экономия не достигается за счёт качества.

## Как запустить PoC

Требуется только Python 3.10+ (стандартная библиотека, без pip install):

```bash
python3 poc/demo.py            # happy path + эскалации на 7 mock-тикетах
python3 poc/demo.py --llm-down # fallback: имитация недоступности LLM API
python3 -m unittest discover poc -v   # smoke-тесты (7 шт.)
```

## Какой сценарий демонстрируется

1. Типовой тикет («забыл пароль») → PII маскируется → тема определена → найдена статья KB → mock-LLM формирует черновик → решение в decision log (**happy path**).
2. Рискованный тикет (двойное списание, номер карты, угроза жалобой) → `risk=high` → **эскалация оператору без генерации ответа** (**risky path**).
3. Бессодержательный тикет → low confidence → эскалация.
4. Нейтральный платёжный вопрос («где посмотреть чек») → черновик генерируется, но категория из списка «только с оператором» → **suggest-режим**: черновик уходит оператору на подтверждение, не пользователю.
5. `--llm-down` → circuit-breaker-поведение: классификация и маршрутизация работают, черновики не генерируются, тикеты уходят операторам (**fallback path**).

## Что реализовано, а что — архитектурный дизайн

| Реально работает (PoC) | Упрощение в PoC | В целевой архитектуре |
|---|---|---|
| PII-маскирование | regex | regex + локальный NER |
| Классификация темы/риска + confidence | ключевые слова, суррогатный confidence | классическая ML-модель на исторической разметке, калиброванные пороги |
| Retrieval по базе знаний | TF-IDF (stdlib), 6 статей | embedding-модель + vector store |
| Черновик ответа | шаблонный mock-LLM | внешний LLM API (вход только маскированный) |
| Эскалация риска / low-confidence, suggest-режим для категорий «только с оператором», decision log (JSONL) | in-process | политика как сервис, append-only хранилище |
| — | вызовы синхронные | очередь (Kafka/RabbitMQ), воркеры, backpressure, дедупликация инцидентов |

## Допущения и ограничения

- ~40% потока действительно типовые (вводная кейса, не проверялась);
- действия операторов пригодны как слабая разметка; база знаний существует и покрывает типовые темы;
- качество rule-классификатора в PoC иллюстративное — см. [SELF_REVIEW.md](SELF_REVIEW.md);
- очередь/асинхронность в PoC не реализованы — только в дизайне ([docs/architecture.md](docs/architecture.md)).
